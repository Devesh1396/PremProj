**2026-09-11.** One YouTube video, fetched LIVE from Apify, run end to end:

```
envelope -> chunks -> claims -> concepts -> delta -> evidence -> strategies -> retrieval
```

then run a second time to prove it is recognised as already known.

**This file is the run report. The OUTPUT ITSELF is in
`first_source_loop_rows.md`** — all 7 claims verbatim, all 71 concept
proposals one per line, the per-claim K10 and K11 decisions, and all 6
strategy cards in full. Sections 3 and 6 below quote examples to make an
argument; the companion file selects nothing. Two of the decisions asked
for there turned out not to be rows at all, which its preamble records.

## 1. The actor fails in two different ways and the build read neither

The very first live call returned **HTTP 201**, from an actor run whose
status was **SUCCEEDED**, carrying one dataset item of 532 bytes:

```json
[{ "videoId": "zg3GBH6fG2I",
   "videoUrl": "https://www.youtube.com/watch?v=zg3GBH6fG2I",
   "videoTitle": "", "channelName": "", "channelId": "", "description": "",
   "viewCount": 0, "likeCount": 0, "commentCount": 0, "subscriberCount": "",
   "durationSeconds": 0, "keywords": [], "thumbnail": "", "publishDate": "",
   "language": "", "selectedLanguage": "",
   "isAutoGenerated": false, "availableLanguages": [],
   "segments": [], "segmentCount": 0,
   "error": "Failed to fetch transcript XML: HTTP 404" }]
```

A retry **63 seconds later** returned 53,701 bytes and 391 segments. Same
video, same request, same token.

`PROGRESS.md` said "the no-captions payload has NEVER been observed.
Nothing asserts its shape." Two shapes have now been observed, and they
are **not the same fact**:

| | `error` | metadata | means |
|---|---|---|---|
| success | *absent* | full | a transcript |
| **no captions** | `"No transcript available for this video"` | **full** | the video has none |
| **read failure** | `"Failed to fetch transcript XML: HTTP 404"` | **all blank** | we never reached it |

Both failure payloads are saved verbatim under
`testing/fixtures/apify/`, alongside a trimmed success.

### What was wrong

`error` was **never read**. Both failures became
`FULL_TEXT_NOT_AVAILABLE`, which is a claim about the *video* and which
is deliberately not rediscoverable — so the first live run of this
adapter permanently recorded a readable video as having no transcript,
and the retry that proved otherwise could not have updated it.

### What was changed

- `youtube_apify.actor_error()` returns the actor's own words, never
  paraphrased.
- `youtube_apify.reached_video()` decides which failure this is from
  **metadata presence**, not from the wording of `error` — a message is a
  string the actor's authors may reword; "did this item come back with a
  title, channel and duration" is a fact about whether the actor got to
  the video page.
- `NoTranscript` carries `transcript_absent`; discovery records
  `FULL_TEXT_NOT_AVAILABLE` only when the actor read the video, and
  `FAILED` otherwise.
- `FAILED` joins `REDISCOVERABLE`, so a retry can overturn it.
  `FULL_TEXT_NOT_AVAILABLE` and `ACCESS_DENIED` stay out: those are
  statements about the source, and re-reading them is the practitioner's
  decision, not a side effect of a poll.

### Still true, and worth keeping

The shape-independent invariant held on a payload nobody had ever seen:
no usable segments meant no transcript, nothing was delivered, no empty
string travelled. **Both** failure payloads set
`isAutoGenerated: false` — not null — so "NULL means not-a-transcript,
never human" is not something this provider gives us for free. What
protects the envelope is that neither item ever gets one.

## 2. The rolling-caption overlap is a timing artefact, not a text one

`PROGRESS.md`: *"the segments OVERLAP … naive concatenation duplicates
words throughout, and downstream it does not look like a joining bug: it
looks like a rambling source."*

Measured on the real 391 segments:

```
segments                                                 391
segments whose start precedes the previous end           386
segments where a text suffix/prefix match was found        1
total words dropped                                        1
```

The timings do overlap, on 386 of 391 pairs. **The text does not.** The
actor returns clean continuations:

```
    0.00 ->  2.16  "You don't have to go to the gym, you"
    1.04 ->  3.84  "don't have to run a marathon, you don't"
    2.16 ->  5.88  "have to do anything crazy. Four very"
```

`dedupe_segments()` gates on timing and then verifies the text, so it
correctly declined to trim 385 of the 386 time-overlapping pairs. The
single trim it did make was this:

```
  seg 389   954.36 -> 958.76   'Woo!'
  seg 390   955.84 -> 958.76   'Woo!'   -> kept: ''
```

A speaker saying "Woo!" twice. The de-overlap ate the second one — the
exact failure its own comment warns about ("a speaker who repeats
themselves must survive intact").

**Net effect on this source: it removed nothing that needed removing and
one thing that did not.** The de-overlap is not harmful at scale — it
only fires on an exact word match inside a time overlap — but the premise
in `PROGRESS.md`, D46 and `test_youtube.py` is wrong for this actor, and
the suite's `OVERLAPPING` fixture is hand-written text redisplay that the
real actor never produces. **Not changed here:** altering the de-overlap
changes the content of every future transcript and the rationale is
recorded in D46. Raised, not routed around.

## 3. Concept normalization matched almost nothing

**20 phrases from K09, 71 proposals across K09 and K11. One resolved.**

```
 AUTO_CREATE | DETERMINISTIC  |  67
 LOGGED      | TRIGRAM        |   4     (the same phrase, four times)
```

The only phrase that reached an existing concept in the whole run:

```
 phrase_norm | insulin resistance
 tier        | DETERMINISTIC (exact)
 resolved_to | insulin resistance [SEEDED]
```

The only near-match any similarity tier produced:

```
 raw_phrase       | Postprandial glucose spike
 tier             | TRIGRAM    similarity 0.778
 nearest_existing | postprandial glucose  [SEEDED]
 decision         | LOGGED   ("low-impact ambiguity, impact=0")
```

This is not a thin seed. The K1 seed holds exactly the right concepts —
`post-meal movement`, `walking`, `post-meal glucose`, `postprandial
glucose`, `skeletal-muscle glucose disposal`, `exercise timing`,
`glucose disposal`, `insulin secretion` — and the run reached none of
them. It created 51 PROPOSED concepts instead, 10 of them over 60
characters and 6 containing a subordinate clause:

```
mitochondria use glucose for energy to contract muscles; uptake does not depend on insulin secretion
soleus muscle possesses high cellular oxidative metabolism and is exceptionally efficient at clearing blood glucose
Repeated interrupted sitting with large-muscle dynamic resistance contractions maintaining recurring glucose disposal
```

Those are sentences, not concepts.

### Three causes, and the middle one is a plain gap

1. The engine answers `target` and `mechanism` with compound phrases and
   whole sentences. `normalize_claim_concepts()` passes them through
   verbatim, and a compound phrase asks for one concept where the answer
   is two.
2. **`normalize_claim_concepts()` calls `resolve()` with `llm=None`.**
   The resolver has an LLM tier that exists precisely for "the cheap
   tiers cannot answer", and K09 can never reach it. Every unmatched
   phrase falls straight through to `_propose_new`.
3. pgvector is absent here — the documented VPS floor — so the semantic
   tier cannot run either. With trigram unable to span a four-word phrase
   and a forty-character concept name, **alias and structured matching
   are the only tiers that can ever fire from K09 on this configuration.**

`status='PROPOSED'` keeps these out of retrieval, which is the mitigation
working. But the downstream cost is visible one stage later: **4 of 6
strategies carry no canonical concepts**, each recorded as an OPEN
`knowledge_gaps` row saying nothing will retrieve it (D8 behaving
correctly over a bad input).

**Not changed here.** Passing an LLM into K09's resolver is a spending
decision and a change to D2's cheapest-first ordering; both belong to the
practitioner and to `DECISIONS.md`, not to a run report.

## 4. Evidence was joined to claims by a time window

`knowledge_synthesize.evidence_for()` was:

```sql
select evidence_id from evidence_records
 where created_at >= (the claim's created_at)
 order by created_at desc limit 20
```

That is not a provenance edge. Seven claims came out of one video and six
were researched in one batch, so the **first** claim collected **all 16**
evidence records — including four studies of a mulberry-leaf supplement
researched for a completely different claim. The strategy card built on
it would have cited them as its evidence.

Every suite passed over this because **every fixture researches one
claim**, and with one claim "written after this claim" and "written for
this claim" return the same rows. The fixture could not tell the right
answer from the wrong one (V2).

**Fixed:** migration `031` adds `evidence_records.claim_id`
(`ON DELETE SET NULL` — the study exists independently of the claim that
led us to it, which is D10). K10 writes it, K11 reads it. Pre-existing
rows are left NULL rather than back-filled by timestamp — the timestamp
is exactly the signal that was proven unreliable — and
`v_evidence_without_claim` separates "older than the link" from "the link
exists and this row still has none".

Measured after the fix, on the card in §6:

```
attached by the claim link : 2   (Hamilton 2022, Buffey 2022)
would have been attached    : 16
```

## 5. A third defect: K10 could never record an identifiable study

The first live research batch crashed:

```
psycopg.errors.IndeterminateDatatype: could not determine data type of parameter $1
  scripts/knowledge_research.py:148  in study_item
```

`study_item()` used bare `%s is not null` parameters. Postgres cannot
infer a type for those and raises before the query runs. The identical
bug, with the identical fix and an explanatory comment, was already in
`knowledge_discover.already_known()`.

It survived because every evidence fixture in the suite has **no** DOI,
PMID or URL, so `study_item()` returned at its first branch and the SQL
below it had never executed in any test. The one assertion over it —
"a study with no DOI, PMID or URL gets NO source_item" — tested the
early return.

**Fixed** with explicit `::text` casts, plus coverage that drives the
branch that touches the database: an identifiable study gets a
`source_items` row carrying its identifiers, the same study cited twice
is one row, and it is filed under K10's own independent-evidence source
rather than the video (D10). Reverting the fix turns that suite red.

The timestamp resolves. `[04:12]` is a chunk whose text is byte-identical

> **expected_magnitude_summary** — Modest and variable for brief 5–10

> contractions; a 5–10 minute bout provides minor, incremental glucose

came from a multi-hour protocol and that brief bouts have limited direct

## 8. RUN 2 — the same video, immediately

Re-run seven minutes later, whole loop, live fetch again.

```
  chunks                   13 -> 13    same
  claims                    7 -> 7     same
  concept_proposals        71 -> 71    same
  concepts_proposed        51 -> 51    same
  creators                  1 -> 1     same
  delta_analyses            1 -> 1     same
  documents                 1 -> 1     same
  evidence_records         16 -> 16    same
  knowledge_gaps            4 -> 4     same
  source_items             14 -> 14    same
  strategies                6 -> 6     same
  envelopes                 1 -> 2     >>> CHANGED
  source_fetches            1 -> 2     >>> CHANGED
```

Same rows, not merely the same counts: nothing in `claims`,
`strategies`, `concept_proposals`, `evidence_records` or
`knowledge_chunks` has a `created_at` later than RUN 1.

### Which mechanism caught it — two, at two layers

**Discovery, on the URL.** `register_item()` found the existing row by
canonical URL and bumped `last_seen`; `external_id = zg3GBH6fG2I` is the
fallback behind it. One item, seen twice:

```
 item_id          | eec6a774-74cc-4656-8a3e-49440a6bd847
 ingestion_status | NORMALIZED        (not reset — NORMALIZED is not REDISCOVERABLE)
 first_seen       | 05:31:22.738
 last_seen        | 05:38:29.868
```

**Ingest, on the content hash.** Both fetches returned exactly 53,701
bytes, so the rendered markdown hashed identically and §57 fired.

### A second envelope row IS created — deliberately, and it says something false

```
 envelope_id    | c038a016-310c-48db-a0b2-3de14ed626f4
 status         | DEDUPED
 duplicate_of   | 7860613f-0ccc-4a51-838a-ad950288ef52
 source_version | 2
 content_hash   | (null)
 raw_preserved  | f
```

The row is intentional — `open_envelope()`: *"DEDUPED keeps the row: the
practitioner handed this over and the record that they did is worth as
much as the content."* Nothing was re-extracted and nothing was paid for
twice. But two things on it are wrong:

1. **The receipt says the source changed, and it did not.** §56's URL
   versioning runs *before* §57's hash dedup, unconditionally, so the
   note reads *"version 2 of this URL — the source changed since it was
   last ingested"* for byte-identical content. A monitored URL polled
   daily reaches `source_version` 365 with one distinct document.
2. **`content_hash` is NULL on the DEDUPED row** — it is only written on
   the non-duplicate path — so the row that exists because of a hash
   match cannot be found by that hash.

Reported rather than fixed quietly, per the standing instruction on
RUN 2.

## 10. Also found: the suites do not clear their own fixtures

`CLAUDE.md` requires tests to be idempotent **and** to clear their
fixtures. They re-run cleanly; they do not clean up. Running
`test_knowledge_factory.py` against this database left claims, evidence
records, source items and strategies behind, and once a live run was in
the same database the residue was indistinguishable from it by row shape
alone.

`clear()` in `test_knowledge_factory.py` never touched
`evidence_records` at all, so every run of that suite added studies to
the library permanently. Fixed there (deleted before the claims, since
`claim_id` is `ON DELETE SET NULL` and dropping the claims first orphans
the rows and takes the only handle on them with it). **The wider gap is
not fixed** — `test_youtube.py`'s `clear()` also leaves claims and
proposals behind, and the general rule needs a pass of its own.
